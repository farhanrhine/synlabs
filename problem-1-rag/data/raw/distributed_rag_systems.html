Distributed Retrieval-Augmented Generation (RAG) Architecture

Chunking Strategies for Document Ingestion

Chunking is the foundational step of any RAG pipeline. If chunk size is too small (e.g. under 100 characters), semantic context is lost. If chunk size is too large (e.g. over 2000 characters), irrelevant noise dilutes the retrieved embedding vector.

The standard industry default for technical corpora is a sliding window chunk size of 500 characters with an overlap of 100 characters. Overlap guarantees that sentences spanning chunk boundaries maintain coherent continuity.

Idempotent Ingestion Principles

Production document pipelines frequently re-index document repositories upon webhook notifications. An idempotent ingestion pipeline must ensure that re-submitting unchanged documents does not generate duplicate vectors or inflate index memory.

This is achieved by computing a deterministic cryptographic hash (such as SHA-256) over the document content, chunk index, and document identifier, deriving a stable UUIDv5. When upserting into the vector store, the point ID replaces the existing record in place without growing the total vector count.

Grounding and Hallucination Prevention

LLMs are prone to hallucinating plausible-sounding answers when retrieval returns irrelevant or low-similarity chunks. To mitigate this risk, production RAG systems employ two critical guardrails:

  • Similarity Threshold Filtering: Chunks whose cosine similarity falls below a strict threshold (e.g., 0.55 or 0.60) are discarded before prompt assembly.
  • Explicit Refusal Prompting: The system prompt explicitly commands the model to output a standardized refusal phrase ("The available documents do not contain sufficient context") whenever retrieved context fails to answer the question directly.
  • Verifiable Citations: Answers must cite the exact chunk identifiers used to substantiate each factual claim.
